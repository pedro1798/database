# 식재료 매니저-채움

'채움'은 매장의 식재료 입고·소비·폐기, 레시피와 판매, 공급처와 구매 정보를 연결하여 재고 관리와 구매 의사결정을 지원하는 서비스입니다.

## 1. 프로젝트 배경과 목표

식재료를 사용하는 매장은 판매량 예측 실패로 인한 재고 부족 혹은 과잉 구매에 따른 폐기, 공급가격 변동을 함께 관리해야 합니다. 이 프로젝트는 재고의 현재 수량뿐 아니라 수량과 비용이 변한 이력을 저장하고, 레시피·판매·구매 데이터를 연결하는 것을 목표로 합니다.

- 식재료별 입고·소비·폐기 이력을 추적합니다.
- 매장별 레시피와 판매 기록을 관리합니다.
- 공급처별 상품과 가격 이력을 비교합니다.
- 재고 소진 예측과 발주 판단에 필요한 데이터를 제공합니다.

## 2. 주요 기능 및 구현 목표

| 영역 | 목표 기능 | 필요한 저장 데이터 |
| --- | --- | --- |
| 재료 관리 | 재고 조회, 품목별 소비·폐기 통계, 폐기비용 조회 | 입고 배치, 소비·폐기 기록, 매입단가, 재고 조정 기록 |
| 레시피 관리 | 메뉴 등록, 1인분당 재료 구성 관리 | 매장별 메뉴, 식재료, 재료별 사용량 |
| 판매 관리 | 메뉴별 판매량·매출 조회, 식재료 기준 추정 이윤 | 메뉴별 일일 판매 수량과 실제 매출액 |
| 구매 관리 | 주문 내역, 월 구매액, 입고 추적, 입고 배치 |
| 공급처 관리 | 공급처 정보, 공급가격 추이 | 공급 상품, 규격, 가격 확인 일시와 출처 |
| 예상 소진일, 추천 발주일, 임계점 이하 자동발주 | 소비 이력, 매장별 발주 설정, 공급 소요일 |

자동발주, 예측, 통계 계산은 애플리케이션에서 처리합니다. 데이터베이스는 계산에 필요한 원본 기록과 사용자 설정을 보존합니다.

## 3. 데이터 설계 방향

### 현재 ERD에 반영된 구조

| 엔티티·관계 | 역할 |
| --- | --- |
| STORE | 매장 이름, 연락처, 주소 |
| PROVIDER | 공급처 이름, 연락처, 주소 |
| INGREDIENT | 식재료 이름, 분류, 기준 단위 |
| RECIPE | 매장에 속한 메뉴와 현재 판매 가격 |
| INVENTORY_BATCH | 매장·공급처·식재료별 입고 배치, 수량, 매입단가, 소비기한 |
| SALES | 메뉴별 판매일과 판매 수량 |
| STOCK_OUT | 배치별 소비·폐기 수량, 발생 일시와 사유 |

RECIPE는 현재 매장에 종속되는 약한 엔티티로 설계되어 있습니다. 같은 매장 안에서 Recipe_Name이 유일하다는 전제하에 논리 스키마에서는 `(Store_id, Recipe_Name)`으로 식별합니다.

## 4. 데이터 저장 원칙과 제약

### 단위와 가격

- 각 식재료는 kg, L, 개 등 하나의 Base_unit을 가집니다.
- 입고량·소비량·폐기량·레시피 사용량·재고 설정은 해당 기준 단위로 통일합니다.
- 공급 상품에는 포장당 기준 수량을, 가격 이력에는 포장 가격을 저장합니다.
- 주문 상세에는 기준 단위로 환산한 주문 수량과 확정 단가를 저장합니다.
- 배치에는 기준 단위당 실제 매입단가를 저장합니다.
- 서로 다른 단위의 수량을 그대로 합산하지 않습니다. 단위 변경 시 과거 기록의 의미가 바뀌지 않도록 변경을 제한하거나 명시적으로 변환합니다.

### 기록의 식별과 일관성

- 판매는 메뉴별 일일 집계이며, 같은 메뉴·같은 날짜의 기록은 하나만 저장합니다.
- 매장·식재료 조합마다 STOCK_POLICY는 하나만 존재합니다.
- 일반 수량은 양수로 저장하고, 재고 조정량은 증감 방향을 구분할 수 있도록 부호를 허용합니다.
- 소비·폐기·조정을 반영한 배치 잔량이 음수가 되지 않도록 처리합니다.

### 과거 기록 보존

- 현재 메뉴 가격으로 과거 매출을 다시 계산하지 않습니다.
- 최신 공급가격으로 과거 구매금액을 다시 계산하지 않습니다.
- 소비·폐기와 실사 조정은 서로 다른 종류의 기록으로 남깁니다.
- 실제 입력한 소비와 판매·레시피로 생성한 소비를 구별하고 중복 차감을 방지합니다.
- 과거 거래가 참조하는 메뉴와 공급 상품은 삭제보다 비활성화를 우선합니다.
- 메뉴명 변경, 레시피 변경 시 과거 기록을 어떻게 보존할지는 논리 스키마 확정 전에 정합니다. 과거 레시피 기준 원가를 재현하려면 레시피 버전 또는 당시 계산 근거를 추가로 보존해야 합니다.

## 5. 애플리케이션에서 계산할 정보

| 결과 | 계산 근거·주의사항 |
| --- | --- |
| 현재 재고 | 입고량 − 소비량 − 폐기량 + 재고 조정량 |
| 일평균 소비량 | 선택 기간의 소비량과 기간 일수. 실측·추정 여부 구분 |
| 폐기비용 | 폐기량 × 해당 배치의 매입단가 |
| 예상 소진일 | 사용 가능한 재고와 평균(2주) 소비량. 소비량 0이면 계산 불가 처리 |
| 발주 추천·자동발주 | 임계점, 목표 재고, 입고 대기량, 공급 소요일을 반영 |
| 가격 변동률 | 동일 공급 상품의 비교 시점 가격 | 동일 단위·규격·품질과 가격 확인 시점을 고려 |
| 월 구매액 | 주문일 기준 또는 입고일 기준 중 하나를 명시 |
| 메뉴별 추정 이윤 | 실제 매출에서 선택한 기준의 식재료 원가 차감. 인건비 등은 별도 |

소비기한이 지난 재고는 사용 가능 재고와 구분합니다. 소비 비율과 판매 비율은 수량 기준인지 금액 기준인지 명시합니다. 공급가격 데이터의 수집 방법과 갱신 주기는 별도로 확정합니다.

## 6. 주요 이용 흐름

1. 매장과 공급처, 식재료를 등록합니다.
2. 매장별 메뉴와 1인분당 식재료 사용량을 등록합니다.
3. 매장에서 관리할 식재료를 등록합니다.
5. 입고 시 배치별 수량·단가·입고일·소비기한을 기록합니다.
6. 메뉴별 일일 판매와 배치별 소비·폐기를 기록합니다.
7. 재고 실사에서 차이가 발견되면 조정 기록을 남깁니다.
8. 축적된 기록으로 통계·예측을 조회합니다.

레시피 등록 시 식재료 관리 목록을 생성한다는 것은 기존 테이블에 매장별 관리 기록을 추가한다는 의미입니다. 레시피마다 새로운 데이터베이스 테이블을 생성하지 않습니다.

## 8. 수정사항

1. 상품 주문 관리의 필요성을 느끼지 못해서 ORDER Entity를 삭제했습니다.
2. 공동구매 서비스를 지원하지 않고 재고 관리에 집중하기로 했습니다.
3. 발주 시점을 알리기 위해 Reorder_point를 사용하고 대신 Safety_stock은 삭제했습니다.
4. 폐기 이유를 남길 필요성을 못 느껴서 STOCK_OUT의 Reason을 삭제했습니다.
5. Provider의 주소 정보를 삭제했습니다.
